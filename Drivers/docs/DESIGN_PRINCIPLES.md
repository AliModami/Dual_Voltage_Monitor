# 1- اصل اول
# هر ماژول فقط یک مسئولیت دارد.

-------------------------------------------------------------------------------

هر فایل باید فقط یک وظیفه مشخص داشته باشد.

نمونه صحیح:

buttons.c

↓

مدیریت کلیدها

نمونه نادرست:

buttons.c

↓

مدیریت کلیدها

↓

نمایش روی LCD

↓

ذخیره در Flash

---

# 2- اصل دوم
# وابستگی حداقلی

-------------------------------------------------------------------------------

هر ماژول باید کمترین وابستگی ممکن را به سایر ماژول‌ها داشته باشد.

وابستگی کمتر یعنی:

• تست آسان‌تر

• توسعه آسان‌تر

• نگهداری ساده‌تر

---

# 3- اصل سوم
# پنهان‌سازی جزئیات

-------------------------------------------------------------------------------

هر ماژول فقط API عمومی خود را در اختیار دیگران قرار می‌دهد.

تمام متغیرها و توابع داخلی باید Private باشند، مگر اینکه واقعاً نیاز به دسترسی عمومی وجود داشته باشد.

---

# 4- اصل چهارم
# طراحی قبل از کدنویسی

-------------------------------------------------------------------------------

قبل از نوشتن حتی یک خط کد باید مشخص شود:

• هدف فایل چیست؟

• مسئولیت آن چیست؟

• API آن چیست؟

• وابستگی‌های آن چیست؟

---

# 5- اصل پنجم
# خوانایی مهم‌تر از کوتاهی کد است

-------------------------------------------------------------------------------

کدی که شش ماه بعد به‌راحتی قابل فهم باشد، از کدی که فقط کوتاه‌تر است ارزش بیشتری دارد.

---

# 6- اصل ششم
# مستندسازی بخشی از توسعه است

-------------------------------------------------------------------------------

کد بدون مستندات کامل محسوب نمی‌شود.

هر فایل باید شامل:

• هدر حرفه‌ای

• توضیح هدف

• توضیح معماری

• توضیح توابع

• تاریخچه تغییرات

باشد.

---

# 7- اصل هفتم
# بدون اعداد جادویی

-------------------------------------------------------------------------------

از نوشتن مقادیر ثابت در بدنه کد خودداری شود.

به جای:

```
HAL_Delay(150);
```

از:

```
#define BUZZER_SHORT_TIME_MS   150U
```

استفاده شود.

---

# 8- اصل هشتم
# نام‌گذاری گویا

-------------------------------------------------------------------------------

نام متغیرها، توابع و فایل‌ها باید بیانگر نقش آن‌ها باشد.

از نام‌های مبهم مانند:

```
temp

data2

func

new
```

اجتناب شود.

---

# 9- اصل نهم
# طراحی مستقل از سخت‌افزار

-------------------------------------------------------------------------------

منطق برنامه نباید مستقیماً به HAL یا GPIO وابسته باشد.

در صورت امکان، از لایه‌های انتزاعی (Framework) استفاده شود.

---

# 10- اصل دهم
# هر Commit یک هدف

-------------------------------------------------------------------------------

هر Commit باید فقط یک تغییر مشخص را شامل شود.

نمونه مناسب:

```
Add Button Application Layer

Refactor Display Framework

Implement Buzzer State Machine
```

---

# 11- اصل یازدهم
# Build بدون خطا

-------------------------------------------------------------------------------

هیچ Commit نباید شامل خطای کامپایل باشد.

هدف پروژه:

```
0 Errors

0 Warnings
```

---

# 12- اصل دوازدهم
# آموزش در دل کد

-------------------------------------------------------------------------------

کامنت‌ها فقط نباید بگویند «چه کاری انجام می‌شود»، بلکه باید توضیح دهند «چرا» آن کار انجام شده است تا مطالعه کد جنبه آموزشی نیز داشته باشد.

---

# 13- اصل سیزدهم
# قابلیت استفاده مجدد

-------------------------------------------------------------------------------

هر ماژول باید تا حد امکان به گونه‌ای طراحی شود که در پروژه‌های آینده نیز قابل استفاده باشد.

---

# 14- اصل چهاردهم
# توسعه تدریجی

-------------------------------------------------------------------------------

ابتدا نسخه ساده و پایدار پیاده‌سازی شود.

سپس قابلیت‌های جدید به‌صورت مرحله‌ای اضافه شوند.

---

# 15- اصل پانزدهم
# بازبینی قبل از Commit

-------------------------------------------------------------------------------

• تغییرات منطقی و محدود به همان هدف
